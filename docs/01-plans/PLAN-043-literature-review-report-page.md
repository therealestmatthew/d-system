# Literature-review campaign report page

Build a generated, navigable HTML report over the nine-session adversarial literature-review
campaign. Requirements: [REQ-027](../06-requirements/REQ-027-literature-review-report-page.md).

## Why this is four phases and not one

The report has four separable concerns, and three of them can fail independently of the others:
reading the campaign's files into a structured form, rendering Markdown faithfully, making three
large tables interactive, and tying the whole thing together with cross-links and the epistemic
framing. A single phase would mean one session carrying a Markdown renderer, a 43-column table UI
and a 1,200-row performance bound at once.

The sequencing is forced by data flow: nothing can render before extraction produces a stable
shape, and cross-linking (`phase-lrr-04`) needs both the rendered deliverables and the tables to
have anchors to point at.

## Design

Follow the `generate_overview.py` precedent exactly, because it already solves this problem shape
and is the repository's only shipped deterministic page generator:

- **The generator computes nothing.** It reads `research/literature-review/`, and every count on
  the page comes from those files. This is `REQ-027` R05, and it is what makes the drift test
  meaningful.
- **Templates carry the markup**, under `templates/html/` with `{{TOKEN}}` substitution and a token
  contract commented at the top of each template, alongside a stylesheet in `templates/styles/`.
- **No wall clock in the output path.** Any generated-at label derives from source data. Two runs
  against an unchanged tree produce identical bytes.

### The one real design question, and the answer

**Does the 2.7MB of CSV go into the page or beside it?** Inlining all three tables as JSON makes a
single self-contained file of roughly 3MB, which meets R08 trivially but risks R10's interactivity
bound. Loading them as separate local JSON files keeps the entry page small but makes "opens from
the filesystem with no build step" harder, since `file://` blocks some fetch patterns.

**Decision: inline, with the matrix and inventory deferred behind their own views.** The entry page
and the rendered deliverables carry no table data. Each table view carries its own data inline in
the page that shows it, so the ledger's 1.6MB is paid only when the reader opens the ledger. This
keeps R08 clean (no fetch at all) and gives R10 a fighting chance. If the ledger still misses the
500ms bound, the fallback is virtualised rows, not a fetch.

Recorded here rather than as an ADR because it is a build choice inside one plan, reversible by
changing the generator. If it turns out to constrain the design system generally, it earns an ADR
then.

## Phases

| Phase | Outcome |
|---|---|
| `phase-lrr-01` | Deterministic extraction: campaign files to a stable structured form, with counts |
| `phase-lrr-02` | Template family, shell and navigation; Markdown deliverables render faithfully |
| `phase-lrr-03` | The three browsable tables, including the 43-column matrix and the 1,200-row bound |
| `phase-lrr-04` | Cross-links, the epistemic framing, the generator assembly, the OPS document and the drift test |

`phase-lrr-01` and `phase-lrr-02` could run concurrently by a pair of agents, since the template
family can be built against a fixture. They are chained anyway: the repository's `max_active` is 3
and two of those slots are routinely in use, so the parallelism would rarely be available, and a
fixture that drifts from the real extractor costs more than the sequencing saves.

## Risks

- **The Markdown in these deliverables is not simple.** `05` and `06` carry nested tables inside
  blockquotes, long verbatim quotations, and section headings generated by different dispatches
  across nine sessions. A renderer that handles `01`'s prose may not handle `05`. `phase-lrr-02`
  verifies against all eleven Markdown deliverables, not a sample.
- **R04's dangling-link bound is strict** and the deliverables cite source ids that were later
  renamed or deduplicated — the campaign has two known duplicate inventory rows and at least one
  matrix row citing a path that 404s. Expect the first honest run of R04 to find real dangling
  references. Those are findings about the corpus, to be reported, not silently linked to
  something plausible.
- **R10's bound may not be reachable with a plain table** at 1,200 rows. The plan names
  virtualisation as the fallback so the phase does not stall on discovering it.

## Out of scope

Everything `REQ-027` lists as out of scope, and in particular any edit to
`research/literature-review/`. If the report reveals a defect in a deliverable, that is an idea and
an owner decision, not a fix folded into a rendering phase.
