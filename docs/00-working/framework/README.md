# Generalized Multi-Developer Agentic Workflow Framework

This directory contains reusable, generalized templates, protocols, and governance structures that can be applied to any new repository using multi-developer, agentic workflows.

## Purpose

Extract the essential patterns from d-system into a portable framework that:
- Enables concurrent work without collisions (branch + claim + worktree model)
- Scales from 1 to many developers across multiple machines
- Works with Claude agents + human developers
- Provides clear decision records and session protocols
- Eliminates friction through generalized templates and validation

## How to Use This Framework

### For a New Hackathon Repo

1. **Copy templates** from `04-templates/`
   - CLAUDE.md, README.md, backlog.yaml, codes-reserved.yaml
   - Customize with your project details

2. **Copy governance docs** from `03-governance/`
   - Reference them in CLAUDE.md
   - Team reads these before starting work

3. **Follow workflows** from `02-workflows/`
   - Planning workflow → get all requirements and plans approved
   - Execution workflow → developers claim and work
   - Concurrent coordination → handle races

4. **Use schemas** from `05-schemas/`
   - Validate requirements, plans, session records
   - Ensures consistency across sessions

5. **Read principles** from `01-overview/`
   - Align team on "why" before "how"

### For Agent Deployment

1. Read `agent-deployment-checklist.md`
2. Use `CLAUDE.md.template` to orient the agents
3. Agents follow the workflows in `02-workflows/` (they're written for machine-readable consumption)

## Agent Workflows for Extraction and Analysis

### Workflow 1: Pattern Extraction Agent
**Goal:** Read d-system docs and extract generalizable patterns

**Agent Instructions:**
```
Read the d-system repository (AGENTS.md, GOV-*.md, ADRs, PLAN documents).
Extract patterns that are:
1. Repeated across multiple documents
2. Applicable to any multi-developer repo (not d-system-specific)
3. Worth encoding as a best practice

Examples to look for:
- Conflict resolution patterns (code allocation, phase claiming, git races)
- Decision documentation patterns (what makes a good ADR/decision record?)
- Session handoff patterns (what info is always captured?)
- Workflow patterns (steps that repeat, optimizations possible)

Output: extracted-patterns.md with:
- Pattern name
- Where it appears in d-system
- Generalized form (how to apply elsewhere)
- Why it works
```

### Workflow 2: Governance Effectiveness Analyzer
**Goal:** Analyze which governance mechanisms actually help vs. overhead

**Agent Instructions:**
```
Analyze GOV-001, GOV-003, GOV-006 and related documents.

For each governance mechanism, determine:
1. What problem does it solve?
2. How many incidents/collisions has it prevented?
3. How much overhead/friction does it add?
4. Is it essential, nice-to-have, or overkill?

Categorize as:
- CRITICAL (no coordination without it)
- IMPORTANT (prevents significant issues)
- NICE-TO-HAVE (improves quality, adds overhead)
- SKIP-FOR-HACKATHONS (too much process for short duration)

Output: governance-effectiveness-study.md with:
- Feature name
- Problem solved
- Incident evidence
- Overhead cost
- Recommendation
```

### Workflow 3: Session Documentation Analyzer
**Goal:** Analyze session records to find patterns and improvement opportunities

**Agent Instructions:**
```
Read all session records in docs/03-sessions/*.md

For each session record, extract:
1. Key decisions made
2. Requirements discovered mid-work
3. Action items / follow-up work
4. Blockers encountered
5. Quality of documentation (clear/vague/incomplete?)

Aggregate findings:
- What decisions recur? → Could be a principle or template
- What requirements are always discovered late? → Better ideation phase?
- What blockers repeat? → Need a mitigation strategy?
- What session records are hard to parse? → Template needs improvement

Output: session-documentation-quality.md with:
- Summary of session record analysis
- What's working well (keep it)
- What's inefficient (improve it)
- Recommended template changes
```

### Workflow 4: Decision Capture Efficiency Analyzer
**Goal:** Measure how efficiently decisions are being made and recorded

**Agent Instructions:**
```
Analyze decision records (ADRs, GOV-003 entries, backlog decisions).

Measure:
1. Decision latency: When was the decision needed vs. when was it made?
2. Visibility: Was the decision visible to affected parties before it was finalized?
3. Reversibility: Could the decision be reversed later if needed?
4. Record quality: Is the rationale clear? Is it auditable?

For each decision category (tech, scope, governance, process):
- How well does the current protocol work?
- What could improve?
- What's the cost/benefit of improvement?

Output: decision-capture-efficiency.md with:
- Findings by decision type
- Latency analysis
- Visibility gaps
- Recommended improvements
```

### Workflow 5: Protocol Enhancement Proposer
**Goal:** Propose improvements to session close/checkpoint protocols

**Agent Instructions:**
```
Read:
- .claude/skills/checkpoint/SKILL.md
- .claude/commands/session-close.md (if it exists)
- GOV-003 notes about session closing
- Recent session records

Analyze:
1. Is the checkpoint/close process efficient?
2. Are agents clear on what to capture?
3. Are there repeated hand-off failures or confusion?
4. Could the protocol be automated further?
5. Are there redundant or missing steps?

Propose:
- Changes to checkpoint skill
- Changes to session-close command
- Template improvements
- Automation opportunities

Output: recommended-enhancements.md with:
- Enhancement proposal
- Problem it solves
- Implementation effort
- Risk/benefit
```

## Key Principles for This Framework

1. **No magic**: Every mechanism has a reason. If it's not solving a problem, it doesn't belong.
2. **Scalable**: Works for 1 developer, 5, 50, or 100 agents. Design for concurrency from the start.
3. **Auditable**: Decisions and disputes are resolved by reading git history + decision records, not by asking people what happened.
4. **Automatable**: Workflows are documented step-by-step so agents can execute them. Humans can follow the same steps.
5. **Portable**: Copy this to a new repo, customize 3 templates, start working. No custom setup.
