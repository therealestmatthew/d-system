# Parked ideas

Generated by `uv run python tools/generate_ideas_md.py` from `_data/ideas.jsonl`. Never edit
this file by hand — it is regenerated and the test fails on any difference. To record an
idea or move one along, use the writer:

```bash
uv run python tools/append_idea.py add --file idea.md   # title = first line, body = the rest
uv run python tools/append_idea.py status 000007 reviewing
```

`--title "..." --body "..."` also exist, but only for a short, plain-text title typed by hand —
prose containing a backtick, `$(...)`, a quote or a newline is not safe as a quoted shell argument.

**Ideas are recorded as given.** They are not deduplicated, merged or judged at entry
([ADR-010](../04-decisions/ADR-010-idea-staging.md)). If an idea overlaps something that
already exists, note the overlap inside the entry — do not decline to record it. Triage is a
downstream process, not a gate at the door.

**The log is append-only and nothing in it is ever edited.** A status change appends an
event; it does not rewrite the entry. That is a fact about the storage now rather than a
rule someone has to keep, and it is why a discarded idea stays visible with its history —
the record of what was considered and rejected is worth as much as the record of what was
kept.

| Status | Meaning |

| `open` | Captured; nothing has looked at it |
| `triaged` | Scouting finished, findings attached; awaiting the owner |
| `reviewing` | The owner is actively considering it |
| `promoted` | Became a plan, requirement or phase — terminal, and names which |
| `discarded` | Rejected — terminal unless revisited, which is permitted once |

## 000002 · Prioritised search order for agentic knowledge retrieval

**Created 2026-09-06T14:47:00-04:00 · Status: `triaged`**

The retrieval system needs a **stated order of places to look**, not just a set of places. An agent
answering "how does X work here?" currently has no guidance on what to consult first, and the sources
disagree with each other in predictable ways.

Candidate sources, roughly in the order they were suggested:

- **Developed code** — the only source that is true about what *exists*
- **Plan documentation** — intent, which may describe things never built
- **ADRs** — why a choice was made, and what was rejected
- **Session records** — contemporaneous narrative, including corrections
- **This ideas list** — speculation, explicitly not yet decided
- Also worth placing: `brain/` memories, the generated glossary, `systems.yaml`, `AGENTS.md`

**The ordering principle is the real question.** These sources have different relationships to truth:
code is what is, plans are what was intended, ADRs are why, session records are what happened, ideas
are what might. An agent that reads a plan describing unbuilt work and treats it as reality will be
confidently wrong — which happened in this repository on 2026-09-06, where several `systems.yaml`
entries describe aspiration and `PROMPT-003` now asks whether the file is a live registry or a map.

Worth deciding when this becomes real:

- Does the order vary by question type? "How does X work" and "why is X this way" plausibly want
  different first stops.
- Should a source carry a **confidence or freshness signal** so the agent can weigh disagreement,
  rather than trusting whichever it read first? `brain/` memories already have a `confidence` field;
  nothing else does.
- What resolves a genuine conflict between sources — is code always authoritative, or does an ADR
  postdating the code win?
- Does this belong in `tools/load_context.py`, in `AGENTS.md` as instruction, or both?

Related: `sys-retrieval`, [PLAN-012](../01-plans/PLAN-012-terminology-system.md) for the glossary as
one such source, and `phase-term-01`'s `--system` filter, which adds a retrieval axis this ordering
would need to account for.

## 000006 · Audit index widths before they run out

**Created 2026-09-06T14:55:00-04:00 · Status: `triaged`**

The ideas list moved to six digits before it had a third entry. Other indexes in this system are
narrower and were not chosen with a horizon in mind.

**Document codes are three digits.** `schemas/document.schema.json` pins the pattern to
`^[A-Z]+-(?:[0-9]{3}(?:\.[0-9]{2})?|[0-9]{4}-[0-9]{2}-[0-9]{2}-[0-9]{2})$` — so `PLAN-999` is the
ceiling per series, sub-codes are capped at `.99`, and dated codes allow only 99 sessions per day.
`GOV-005` says codes are never reused, so retirements consume the space permanently.

Worth auditing: every index in the system against a realistic horizon for reaching a fully
functioning version — document codes per series, sub-codes, dated session sequences, phase numbers
within a track, and anything in `_data/`. Widening a pattern later is cheap; renumbering issued codes
is forbidden by `GOV-005`, so the cost of being wrong is asymmetric.

## 000009 · Independent transcript analysis with adversarial session review

**Created 2026-09-06T15:01:00-04:00 · Status: `triaged`**

An agent that reads the session transcript **directly**, as an independent third party, and writes
its own session documentation. Then run an adversarial review between that record and the one the
working agent produced — two independent accounts of the same session, compared.

The premise has evidence from this session: an adversarial reviewer with no conversational context
returned 21 findings, three of which would have broken the next session. A reviewer that reads the
raw transcript rather than the participant's summary is a stronger version of the same idea, because
the participant's record inherits the participant's blind spots. Two records disagreeing is itself
the signal.

Composes with `000003`, the mid-session notes skill — use both, then diff the accounts.

**Incremental extraction.** A deterministic script to extract the transcript, and a diff between the
current extract and the previous one, so each pass analyses only what is new rather than re-reading
the whole file. Transcripts are large and grow monotonically, so re-analysing from the top gets
expensive fast and produces mostly the same conclusions.

Worth deciding: what the extract format is and whether it is committed or ephemeral; where the
previous extract is stored for diffing; whether the reviewing agent sees the working agent's record
before writing its own, or only afterward — seeing it first risks anchoring, seeing it after costs a
pass; and what happens when the two records disagree on a fact rather than an emphasis.

Related: `000007`, which triages ideas rather than sessions but is the same shape — an independent
pass over a record the primary worker produced.

**Annotations**

## 000048 · An idea scribe agent: a dedicated writer that appends ideas so capture never spends main-session context

**Created 2026-09-08T23:12:58-04:00 · Status: `triaged`**

Recording an idea today happens inline in whatever session the thought came up in: the main
session drafts title and body, writes them to a temp file, and calls
`tools/append_idea.py add --file`, per `.claude/commands/idea.md`. That's cheap for one idea,
but every idea recorded this way spends main-session context on drafting prose that, once
written, the main session never needs to see again — and a session capturing several ideas in
a row (as this one just did, for 000046 and 000047) pays that cost repeatedly.

The proposed agent is a pure writer, mirroring `idea-triage`'s split of "the driver decides
when to invoke, the subagent does the one bounded task": given raw prose (however rough — a
sentence, a half-formed thought, a paste from elsewhere), it distills the title and body per
`idea.md`'s existing guidance ("what the idea is, why it came up, what it would touch, what is
unresolved") and calls `append_idea.py add --file`, using the same file-based-input safety
rule idea-triage already follows for its own writes (never inline prose into a shell
argument — idea 000019's corruption is the standing cautionary example). It reports back the
assigned id and title, not the full body, keeping the round-trip cheap for the caller.

This is a narrower, cheaper counterpart to `idea-triage`, not a competitor to it: this agent
only ever calls `add` (never `annotate`, `status`, `link` or anything else), and it runs at
capture time, before triage ever sees the idea. Same rationale as `phase-idea-01`'s writer
being deterministic tooling — the scribe's job is formatting prose into the sanctioned shape
without judgment, not deciding whether the idea is worth recording. `ADR-010`'s "capture as
given, never filtered at entry" applies here exactly as it does to `idea.md` today: the scribe
records what it's given, it does not decline or merge it into something existing.

Open question: is this worth its own subagent given how cheap the existing `idea.md` command
already is, or does the actual cost belong to whoever is drafting the title/body prose in the
first place — cheapening the round-trip doesn't remove that cost, it just moves it to a model
running at a lower tier (haiku, per idea-triage's precedent). Worth weighing against just
tightening `idea.md`'s own guidance during triage of this idea.

## 000061 · Classify idea nodes by ontological, epistemic, and lifecycle type, not just tags and links

**Created 2026-09-09T03:42:09-04:00 · Status: `open`**

Owner's framing (2026-09-09, recorded verbatim as given, per ADR-010): classifying nodes in
an append-only knowledge graph transforms a flat web of tags into a rigorous ontology, allowing
the system to define not just what an idea is about, but the fundamental nature of the
information it represents. Structuring these classifications as discrete node types rather than
standard tags is what unlocks advanced traversal mechanics — separating an idea's class from its
subject tag allows algorithmic queries like isolating every "Strategic Directive" precariously
linked to an "Assumption" rather than an "Axiom," surfacing structural risk before a line of
code is written.

Three proposed classification axes, each orthogonal to the others and to free-form tags/links:

Ontological classification (the nature of the idea):
- Concepts & Mental Models — theoretical constructs, principles, paradigms (e.g.
  "Observability," "Systems Thinking"). Act as gravitational centers other nodes cluster around.
- Artifacts & Entities — concrete digital or physical outputs: a specific HTML report, a git
  commit, an existing system architecture.
- Processes & Workflows — sequential operations and methodologies; how things are done rather
  than what they are.
- Events — distinct occurrences in time (a system failure, a deployed update, a meeting) that
  trigger new generative thoughts or retrospectives.

Epistemic classification (the truth status of the idea):
- Axioms & Ground Truths — verified, immutable facts within the domain.
- Hypotheses & Assumptions — untested theories or premises that require validation before being
  safely relied on to build code or infrastructure.
- Anti-Patterns & Falsified Concepts — disproven theories, failed plans, known dead-ends.
  Retaining these explicit falsehoods prevents cyclical mistakes and maps the boundaries of the
  system, rather than being discarded once proven wrong.

Execution / temporal classification (the lifecycle stage):
- Generative Seeds — raw, unstructured thoughts captured in the moment, existing purely as
  potential before any plan is formulated.
- Strategic Directives — high-level goals or plans that aggregate multiple seeds into a
  cohesive direction.
- Operational Tasks — executable, granular actions derived from strategic directives.
- Retrospective Insights — post-execution observations derived from a plan after the fact,
  capturing gaps, technical debt, or newly realized context.

Why this doesn't collapse into the existing tag/link design: 000018 (tagging and plan-mapping
system for ideas) proposes free-form/vocabulary tags for discovery, and 000053 (allow ideas to
link directly to plan/document IDs) proposes extending link *targets*. Both are additive,
per-idea metadata. This proposal is different in kind — it argues idea nodes need a small,
closed, structural type system (independent axes: what kind of thing is this, how trustworthy
is it, what lifecycle stage is it in), because graph traversal and risk analysis need to
partition on those axes specifically (e.g. "every Strategic Directive resting on an Assumption
rather than an Axiom") in a way a large open tag vocabulary cannot cleanly support.

Open questions, deliberately unresolved here pending discussion:
- Whether all three axes apply to every idea, or only some (an Event may not have an epistemic
  status the way a Hypothesis does).
- Whether this is a new field on the existing idea schema (schemas/idea.schema.json), a
  separate typed-node system alongside ideas, or the schema for an entirely new "knowledge
  graph" layer that ideas, memories (brain/, docs/05-memories/), and documents all become nodes
  within — see 000060 (memory and context management) and 000032 (evidence-backed provenance
  graph), which already gesture at needing this kind of layer.
- How this interacts with 000004/000005/000043/000044/000045's vector/graph retrieval work —
  whether node type becomes a first-class filter/facet in that retrieval layer.
- What happens to the ~60 existing ideas already in the log if this ships — a backfill/migration
  question, not just a schema-forward one.
- Whether "NetworkX" or a similar graph-processing framework is the intended query surface, or
  whether DuckDB (the existing derived layer) can express the same traversal queries adequately.

## 000063 · Two more idea link types: abstraction (atomic to general) and forking (compound to split parts)

**Created 2026-09-09T03:58:13-04:00 · Status: `open`**

The owner's proposal (2026-09-09), raised while discussing ARCH-005's classification taxonomy:
extend the three existing link types (extends/supersedes/relates_to, schemas/idea.schema.json)
with two more, surfaced by naming a spectrum from atomic/indivisible ideas up through increasing
abstraction:

1. Abstraction. An atomic, concrete idea can be generalized into a higher-level idea that several
   atomic ideas share — that generalization step is itself a relationship, distinct from how
   `extends` is currently defined ("this idea builds on the target"). In practice this session,
   `extends` was already used directionally as "specific idea extends its broader/abstract
   parent" (e.g. 000059 git tooling --extends--> 000058 version control; 000007 --extends-->
   000050 idea management system) — so the open question is whether abstraction is a *tightened,
   explicit* reading of `extends` (child is-a-specialization-of parent) or deserves its own pair
   of directional types (e.g. `generalizes`/`specializes`) so "builds on functionally" and "is a
   more abstract/concrete version of" stop being conflated under one type.

2. Forking / decomposition. An idea introduced too broadly — one that actually bundles several
   distinct ideas — can be split into smaller ideas. This is not `extends` (a fork does not
   necessarily build on the original; the original may end up retired once split) and not
   `supersedes` (supersedes is one-to-one replacement; a fork is one-to-many). It needs its own
   type, asserted on each resulting fragment pointing back at the idea it was split from (working
   name: `forked_from`), with the question of whether the original also gets an explicit inverse
   list of what it was split into, open the same way `linked`'s derived-inverse mechanism already
   handles extends/supersedes.

Both raised as confirmations during discussion, not yet decided: does an abstraction step create
a relationship (yes — the open question is only which type name/direction), and does a fork
create a relationship (yes — this one needs a genuinely new type, since none of the existing
three fit). Not yet resolved: exact type names, whether forking should retire the original
automatically or leave that to the owner's judgment, and whether atomic/indivisible is a status
worth stating explicitly (a leaf node with no further fork possible) or is just the absence of
any outgoing fork edge.

Relates to 000061 (idea node classification) and ARCH-005: the "atomic ideas are indivisible"
framing pairs naturally with an ontological classification, since an atomic idea and a compound
idea that bundles several atomic ones are arguably different kinds of node, not just different
tags.

**Annotations**

- **assessment** by repository-owner (2026-09-09T04:36:50-04:00): Resolved design (owner + agent, 2026-09-09), superseding the original proposal's framing:

- `forked_from` is dropped entirely as a link type. It records provenance of thought, not
  provenance of meaning — valuable for retrospection, but assertion-free about how ideas
  currently relate. Demoted to a new annotation kind proposed in idea 000064, so it stays
  queryable without participating in the relationship graph.

- Direction inverts from the original proposal: atomic ideas compose upward into a compound,
  rather than a compound being torn downward into atomics. A brainstorm-dump "compound idea"
  is not automatically a real thing to decompose — splitting it reveals it was never one node.
  A real compound (system-level emergent meaning, where the whole does something no part does
  alone) is *constructed* bottom-up by asserting that specific atomic ideas function together —
  never *discovered* top-down by forking a bundle apart.

- `component_of` is a new, distinct link type (alongside extends/supersedes/relates_to, not a
  reuse or a derived inverse of extends): atomic idea --component_of--> compound idea. It is
  many-to-many by design — an atomic idea can be a genuine functioning component of more than
  one distinct emergent system, which is exactly why it cannot be modeled as a single-valued
  "born from" edge the way forking would have been.

- `extends` is unchanged and still does real work one level up: once a compound exists as an
  emergent whole, it is itself a node with its own irreducible meaning, and it can `extends` a
  still-more-abstract idea. The result is the same component_of -> extends pattern repeating at
  each level, fractally — not two fixed buckets ("atomic" vs "compound").

- "Atomic" and "compound" are not node types at all — they are structural positions derivable
  from the graph (does anything assert component_of into this node?), not a value to hand-
  classify. This is what ARCH-005's ontological/epistemic axes are actually for: judging whether
  a given multi-idea grouping is a real emergent Concept/Mental Model or an unresolved
  Generative Seed that hasn't been pulled apart yet — a call made on the compound node itself,
  independent of whatever component_of edges exist under it.

Open tension, deliberately unresolved: an Axiom/Ground Truth is meant to be a verified,
indivisible fact, yet it's plausible for an axiom-level idea to itself be composed of several
atomic ideas functioning together (the same fractal pattern as a Concept). Whether that
contradicts the epistemic axis's intent, or whether epistemic status and compositional
structure are simply independent axes that can co-occur, is unresolved and left for when the
axes are tested against real ideas rather than decided in the abstract.

See also: idea 000064 (a lineage annotation kind for thought-progression, replacing forked_from)

## 000064 · A lineage annotation kind for recording thought-progression without shaping the idea graph

**Created 2026-09-09T04:37:02-04:00 · Status: `open`**

Surfaced resolving idea 000063: the original "forked_from" link-type proposal was dropped
because it recorded provenance of *thought* (how the owner actually arrived at an idea), not
provenance of *meaning* (how ideas structurally relate now) — and those turned out to need
different mechanisms entirely, not just different names on the same edge.

Proposal: add a fourth annotation kind alongside the existing note/finding/assessment
(schemas/idea.schema.json's ANNOTATION_KINDS), e.g. `lineage`, reserved for exactly this: "this
idea's content originated while thinking through idea NNNNNN" or "this idea was pulled out of a
brainstorm dump that also produced NNNNNN and NNNNNN." Like `note` and `assessment`, this stays
the owner's own voice (an agent author is restricted to `kind: finding` per
tools/append_idea.py's existing rule) — it's a personal record of process, not something an
agent should be asserting on the owner's behalf.

Why an annotation and not a link: annotations already don't participate in the status machine or
the relationship graph — they accumulate, are queryable, and can be individually corrected via
amend-annotation, but never drive fold()'s derived-inverse or traversal logic the way a `linked`
event does. That is exactly the property this needs: queryable, but structurally inert.

Depends on nothing else shipping first; this is a small, independent schema addition (one new
enum value) that could land alongside or ahead of 000063's `component_of` link type.

## 000065 · A decomposition procedure for compound ideas that don't form a cohesive emergent whole

**Created 2026-09-09T04:37:15-04:00 · Status: `open`**

Follows from resolving idea 000063: a "compound idea" that turns out to be a disjoint
brainstorm-dump, not a real emergent system, needs a defined procedure for pulling it apart —
distinct from simply forking it, since forking (as originally proposed) is no longer how the
system models this at all.

Proposed procedure shape, to be worked out in full once 000062 (a pure classification agent)
and 000055 (a connection-builder agent) exist to actually execute it:

1. A candidate compound idea is flagged (by the owner, or by 000062 classifying it as an
   unresolved Generative Seed bundling more than one distinct concept, per ARCH-005) as worth
   pulling apart.
2. Each fragment is checked against the existing idea corpus before being written — per the
   many-to-many nature of `component_of` (idea 000063's assessment), a fragment may already
   exist as its own idea. If so, no new idea is created for it; instead the *existing* atomic
   idea gains whatever new component_of/relates_to edges the decomposition reveals.
3. Genuinely new fragments are recorded as new ideas via tools/append_idea.py add, each carrying
   a `lineage` annotation (idea 000064) naming the compound idea it was pulled from — history,
   not structure.
4. If, once fragmented, a real emergent grouping is identified among some subset of the
   fragments (the "whole is worth more than the sum" case), that grouping is asserted
   explicitly and separately as its own compound idea, built bottom-up via component_of edges
   from the relevant fragments — never assumed to already exist just because those fragments
   once sat together in the original note.
5. The original compound idea's fate (discarded, amended down to whichever fragment it most
   resembles, or left as-is with lineage annotations pointing away from it) is an open question
   this procedure still needs to settle.

Open questions: whether steps 1-4 are ever automated (agent-driven) or always owner-triggered;
how "already exists" in step 2 is actually checked (semantic search implies 000004/000045's
retrieval work needs to exist first, or this stays a manual/approximate check until then).
