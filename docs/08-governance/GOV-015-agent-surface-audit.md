# Agent surface audit

`phase-agx-02`'s deliverable. Answers three things: a verdict on every file under `.claude/`, a
ruling on whether this repository needs Claude Code specifically or *an* agent runner (idea `000069`),
and a note on which items are ready to demonstrate live and which need hardening first (idea
`000126`'s second purpose). The missing-and-needed finding below answers idea `000013`, which the
plan (`PLAN-031`) rules gets no phase of its own.

## How this was counted

`REQ-016` R03 has two clauses: one row per item under `.claude/`, **and** one row per shipped agent
definition. The two clauses are counted separately, then added.

**First clause.** `find .claude -type f | wc -l` returns **43**. Broken down: 14 files under
`.claude/agents/`, 12 under `.claude/commands/`, 6 under `.claude/prompts/`, 10 `SKILL.md` files
under `.claude/skills/`, and `.claude/settings.json`.

**Second clause.** `git ls-files .codex/` returns exactly one tracked file:
`.codex/agents/idea-triage.toml`. It is `kind: agent` in `agent-workflows/workflows.yaml`, not
`kind: skill` or `kind: command`, which is what makes it a shipped agent definition rather than
context — it earns a row below in its own right, alongside its Claude twin.
`.agents/skills/*/SKILL.md` do not: the same manifest marks every one of them `kind: skill`, so R03's
second clause never reaches them regardless of host. They are read for context below (they bear
directly on the `000069` ruling) but are outside both this phase's deliverables and R03's scope
either way.

The table carries exactly **44** rows — the 43 files under `.claude/` plus the one shipped agent
definition outside it — one row per item R03 names, no more, no fewer.

## Generated versus hand-authored, established before judging anything

`phase-port-02` made part of `.claude/` generated output from `agent-workflows/` via
`tools/generate_agent_workflows.py` (`agent-workflows/workflows.yaml` is the manifest). Cross-checking
the manifest against the file list: **7 of the 43 `.claude/` files are generated** —
`.claude/skills/checkpoint/SKILL.md`, `.claude/skills/log-anti-patterns/SKILL.md`,
`.claude/skills/orient/SKILL.md`, `.claude/commands/idea.md`, `.claude/commands/backlog.md`,
`.claude/commands/idea-triage.md`, and `.claude/agents/idea-triage.md`. Each carries an
`<!-- Generated by tools/generate_agent_workflows.py; do not edit. -->` marker. **Their real source is
`agent-workflows/*.md`, not the `.claude/` file itself.** A verdict of *redesign* against any of these
seven is a verdict against its `agent-workflows/` source, which is outside this phase's declared
deliverables (`docs/08-governance/`, `.claude/`, `docs/04-decisions/`) — this audit reports that
rather than editing either file. None of the seven earns that verdict below; all seven are *keep*.

The remaining 36 files are hand-authored directly under `.claude/`: the demo kit (agents, commands,
skills, prompts built for the 2026-09-15 live demo and its consultant-facing extension), `orient`'s
and `checkpoint`'s and `log-anti-patterns`'s non-generated siblings, `session-start`/`session-close`/
`resume-lit-review`, `d-system-overview`, `partition-adversary`, and `settings.json`.

## Reading "model assignment" and "tooling" for a command or skill

Agents carry an explicit `model:`, `effort:`, `maxTurns:` and `tools:` front matter — those dimensions
are read directly off the file. **Commands and skills carry no such front matter**; they run in
whichever session invokes them, at that session's model, with whatever tools the session already
holds. For those items, "model assignment" is judged as *whether the item appropriately delegates
work that needs a different model* (via the `Agent` tool, to a named agent whose own model is
correct) rather than doing everything in the calling session's model, and "tooling" is judged as
*which tools its instructions actually invoke*, read from its body. Citing the dimension as "not
applicable — runs in-session" is itself a citation, not an omission, and is used below only where the
item genuinely has no delegation decision to make.

**Why redesign rather than keep.** `.claude/` has exactly three functional subdirectories to the Claude
Code harness — `agents/`, `commands/`, `skills/` — plus `settings.json`. `.claude/prompts/` is not one
of them; nothing in the harness discovers or loads a file there, and neither this repository's
`orient` skill nor its own manifest (`agent-workflows/workflows.yaml`) treats it as a fourth category.

## The Claude Code ruling — idea `000069`

**Ruling: this repository needs an agent runner, not Claude Code specifically.** Claude Code is the
current default because it carries the deepest existing investment (the demo kit; most of `.claude/`
is hand-authored, not generated), not because anything about the repository's *governed* work depends
on it structurally.

**What already proves this, independent of the probe.** `phase-port-02` shipped, and this audit
confirmed by `git ls-files`, working Codex equivalents for 7 of the repository's substantive
governed workflows: `.codex/agents/idea-triage.toml` (tracked, and given its own row above under
`REQ-016` R03's second clause) and `.agents/skills/{backlog, checkpoint, idea, idea-triage,
log-anti-patterns, orient}/SKILL.md` (tracked too, but `kind: skill` rather than `kind: agent`, so
outside R03's scope and not rows above). These are not aspirational — they are the same
`agent-workflows/*.md` sources that generate the `.claude/` versions audited above, rendered a
second time for a different host. The portability the idea asks about is not a future question for
the workflows that actually run this repository day to day; it is already built.

**What the Codex capability probe adds.** A real Codex session run against this repository
(`docs/00-working/codex-capability-probe-response.md`) confirms it can perform the coordinator
role this repository's protocols assume — context-isolated sub-agents, nested dispatch, per-dispatch
model selection, and (better than assumed) resuming both completed *and interrupted* agents with
context intact, which satisfies `GOV-013`'s resume-never-re-run rule directly. Its own verdict,
quoted in full in the probe, is that it can do the coordinator job "provided the pack caps concurrent
agents at three, uses terse result contracts, replaces exact context thresholds with milestone
checkpoints, splits question batches to three in Plan mode, and anticipates approval gates." None of
its documented limits (three concurrent workers instead of more, no exposed context counter, no
per-agent turn/token budget, a sandbox that currently excludes the mandated sibling-worktree path) is
a structural blocker — each is a configuration or protocol adjustment, and the probe names the
adjustment for every one of them.

**What stays Claude-Code-specific, and why that is fine.** The demo kit — every `demo-*` agent,
`demo-cmd-*` command, `demo-skill-*` skill, and the six `.claude/prompts/rung-*`/`anti-pattern-gallery`
files above — is built to be shown live inside a Claude Code session, using Claude-Code-specific
mechanisms (`AskUserQuestion`'s recommended-option affordance, the `Agent` tool's named sub-agent
roster). No attempt was made to port it, and none is needed: its entire purpose is presentational for
*this* harness, in front of *this* audience, and that is a one-time, deliberate choice, not evidence
that the repository's ongoing operation depends on Claude Code. Separately, exact numeric turn-budget
enforcement (`maxTurns`, and any future exact-context-percentage protocol per `phase-agx-01`'s R02) has
no Codex equivalent today, full stop — Codex enforces no per-agent turn or token budget natively.

**What would change this answer back toward "Claude Code stays exclusively":**

1. A live (not merely probed) attempt to run this repository's actual worktree-and-claim protocol
   under Codex, after fixing `.codex/config.toml`'s sandbox roots, that still fails on the
   approval-escalation gate for ordinary git operations the protocol requires without a human present
   for every one of them.
2. A governed protocol that turns out to depend on exactly four `AskUserQuestion`-style choices, or on
   an exact context-remaining percentage, in a way milestone-based batching-to-three cannot satisfy —
   none has been found yet, and `GOV-006`'s own batch guidance already says "up to four," not
   "exactly four."
3. The owner deciding the demo kit's mechanisms need porting after all — nothing in its current use
   requires that, but the scope would change if the demo kit stopped being a one-time presentational
   artifact and became part of the repository's ongoing operation.

Because the answer is not "Claude Code stays," `ADR-021` records this decision — naming what is kept,
what is dropped, and which capabilities have no equivalent elsewhere, per `000069`'s own verification
bar.

## Demo-readiness summary — idea `000126`'s second purpose

**Ready to show as-is, no hardening:** every pure-conversation demo item that touches no file —
`demo-cmd-askme`, `demo-cmd-context-check`, `demo-cmd-explain-this`, `demo-cmd-rubber-duck`,

to argue against — run a warm-up prompt immediately before it, every time, or it has nothing to work
with. `demo-skill-ask-me` should be demonstrated before `demo-skill-brainstorm`/`demo-skill-scorecard`
call it, so the audience recognizes the hand-off ("calling demo-skill-ask-me...") when it happens
rather than seeing it cold.

**Needs a hardening pass before being shown live:** `demo-skill-flowchart` and `demo-skill-scorecard`
both write a self-contained HTML file to disk and expect it to be opened in a browser afterward. On
an unfamiliar demo machine this is the one step that can fail in front of an audience — a write
permission, a missing `~/demo-kit-output/` parent, no default browser association for `.html`.
Rehearse the exact write-and-open sequence on the actual demo machine beforehand; do not rely on the
skill files' own correctness as proof the live mechanics work. `demo-skill-scorecard` carries an
additional, self-documented reason to re-check: its own file records a prior real arithmetic bug (a
reported total of 4.10 against scores summing to 4.00) that the "recompute before reporting" rule now
guards against — worth exercising once in rehearsal specifically, not just trusted because the fix is
written down.

**Governed, not demo, but worth knowing before showing anything from this repository on stage:**
`session-close`, `session-start`, `checkpoint`, `log-anti-patterns`, `orient`, `backlog`, `idea`,
`idea-triage` are this repository's real operating machinery, not demo material — showing them live
means showing the actual repository's actual locks and actual idea log, which is a different risk
profile (real state, real consequences) from the self-contained demo kit and should not be treated as
interchangeable with it.
