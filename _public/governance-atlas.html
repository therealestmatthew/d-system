How to read this page

This page explains the repository's governance system in one place: the document codes, the backlog and its claims, the GOV documents, and the idea log. It is a rendering, written by hand from the governed documents each section names. Where it and those documents differ, the documents win.

It carries no live counts. The tables list what existed on the date in the header; run the commands named in each section for the current state.

1. Document codes and the allocator

Every governed document has two identifiers. Its id, such as doc-backlog-protocol, is the permanent key that other documents and the backlog use to refer to it. Its code, such as GOV-002, is the catalog number people read: it starts the filename and orders the document within its series. The validator keeps both unique (ADR-006).

The series are registered in docs/08-governance/codes.yaml, which GOV-005 calls the only source of truth for prefix, numbering and location:

Counter codes

PLAN-036, PLAN-003.01

A prefix and three digits. Plans may add a two-digit sub-code for a child plan, and a sub-code and a parent field must appear together.

Dated codes

SESS-2026-10-04-08

A prefix, the document's own created date and a same-day sequence. The date in the code must equal created.

Filenames

<code>-<slug>.md

The filename starts with the code. The slug may be renamed; the code may not, once the document is on dev.

Allocating a code

Never pick a number by hand. Ask the allocator, which takes the document's kind, not its prefix:

  • uv run python -m src.governance --next-code adr
  • uv run python -m src.governance --next-code plan --parent doc-html-00-overview for a child plan
  • uv run python -m src.governance --next-code session

It prints one code and nothing else, and only after a clean governance check. A gap in a series is never refilled. The allocator also records a short-lived reservation for the code, so two agents asking at once get different numbers.

Reservations and retirements

MechanismWhere it livesWhat it does
Register reservationreserved: in codes.yaml, trackedHolds a code for a phase whose deliverable is that document. Allocation skips it. The entry is removed in the same change that adds the document.
Pre-merge reservationA file under the git common directory, untracked and machine-localWritten by --next-code so parallel sessions do not collide. It expires after a fortnight; --release-code <code> drops it early.
Retirementretired: in codes.yamlRecords a code whose document was deleted. A retired code is never issued again.

Before a branch merges, its codes are free: if a peer took the same number first, whoever integrates second renumbers. After the merge a code is permanent (AGENTS.md, GOV-005).

2. The backlog and the claim model

All planned work lives in docs/09-backlog/backlog.yaml as phases, each sized for one working session. The copy on dev is also the lock table: claiming a phase means writing to it, and the governance check is the lock check (GOV-002, AGENTS.md).

What a phase records

FieldMeaning
idPermanent phase-<track>-NN. Never reused for different content.
plan, sourcesThe governing plan and other source documents, by doc-* id, not by code.
systemsThe registered systems the phase changes. Two active phases may not share one.
deliverablesThe paths it will write. Two active phases may not overlap.
depends_onPhases that must be complete before this one starts.
scope, acceptance, verificationWhat to do, the conditions that prove it done, and the commands that check them.
ideasSix-digit idea ids the phase's own text names. Every id must exist in the idea log.
status, agentWhere the phase is, and which agent holds it while claimed.
session, completion_evidence, resultRequired together when the phase is complete.

States

StateMeaning
readyQueued, and every dependency is complete. --ready lists it.
waitingQueued, but a dependency is unfinished.
activeClaimed by one agent, being worked in its own worktree.
blockedStopped on something outside the phase; needs blocked_reason and resume_when.
deferredHeld back on purpose; needs blocked_reason and resume_when.
completeDone, with evidence and an independent review.
cancelledWill not be done; needs blocked_reason. The id is kept.

Ready and waiting are not stored: both are queued in the file, and src.governance.backlog.readiness computes which. The queue order puts the phases listed in next_up first, then the rest by priority and id.

Claiming and finishing a phase

  1. Orient. uv run python -m src.governance --ready shows the ready phases, the active claims and a Conflicts column naming any peer that already holds one of a phase's systems or paths.
  2. Claim on dev. In one small commit: set status: active, add agent: agent-<name>, and regenerate the catalog. The validator rejects the claim if it overlaps an active phase's systems or deliverables, shares a dependency chain with one, or exceeds the configured max_active.
  3. Work in a worktree. git worktree add -b agent/<phase-id> ../d-system-worktrees/<phase-id> dev. The primary checkout's branch is never switched; the claim commit is the only work done there.
  4. Verify and review. Run the phase's verification commands, write the session record, and have an independent adversarial reviewer check the diff against the acceptance conditions.
  5. Rebase and ask. git rebase dev, rerun the checks, then ask the owner. Integration is a fast-forward onto dev and only happens with the owner's approval.
  6. Complete. A small commit on dev right after the merge sets status: complete with the evidence.
Owner ruling, GOV-003, 2026-09-16

A coordinator may mark a phase complete only when all three hold: the verification ran green with its output recorded; an independent adversarial review of the diff against the acceptance ran and its findings are fixed or explicitly accepted; and the branch was integrated onto dev with the owner's approval.

Owner-directed work with no phase runs unclaimed on an agent/<slug> branch; there is nothing to lock, and peers hold no claim against it.

What makes a document governed

Every Markdown file under docs/ is governed, apart from a short exempt list and the ungoverned staging folder docs/00-working/ (ADR-010). A governed document opens with front matter that schemas/document.schema.json checks:

  • schema_version, id, code, title, kind, status, owner, created, updated, systems and depends_on are required.
  • parent, supersedes, review_after, completion_evidence and tags are optional; nothing else is allowed.
  • References in depends_on, parent and supersedes must resolve and may not form a cycle.
KindLegal statuses
plandraft, approved, active, complete, deprecated, superseded
adrdraft, accepted, deprecated, superseded
every other kinddraft, active, deprecated, superseded

A superseded document must be named in its replacement's supersedes list; a plan nothing replaces becomes deprecated. A complete plan needs completion_evidence.

The catalog and the check

uv run python -m src.governance --catalog regenerates docs/08-governance/catalog.md: every document, every plan with its phase counts, and the held codes. uv run python -m src.governance must exit 0 before work is finished. It checks the documents and the code register, the backlog against the documents, systems and ideas, and fails if the committed catalog differs from a fresh render.

4. The idea lifecycle and the sanctioned writer

Everything the owner asks for is captured as an idea in _data/ideas.jsonl. The file is an append-only event log: each line is something that happened to an idea, and no line is ever edited or removed (schemas/idea.schema.json). An idea's id is six digits, such as 000556.

EventWhat it records
createdThe idea was captured, with a title and body recorded as given.
statusIts status moved, from a stated status to a new one.
revisitedA discarded idea was reopened, once, returning it to reviewing.
amendedA field of an earlier event was corrected, without rewriting that line.
annotatedA note, finding or assessment was added. Allowed on closed ideas too.
linkedA typed relationship to another idea or to a governed document.
classifiedIts record kind and four axis values under ARCH-005; the latest wins.

Statuses

StatusMeaningCan move to
openCaptured; nothing has looked at it.triaged, reviewing, promoted, discarded, delivered, resolved, absorbed
triagedScouted for related work; waiting for the owner.reviewing, promoted, discarded, delivered, resolved, absorbed, set_aside
reviewingThe owner is considering it.promoted, discarded, delivered, resolved, absorbed
promotedBecame a plan, requirement or phase; in flight. Needs promoted_to.delivered
set_asideHeld out of a partition without being discarded.triaged, reviewing
deliveredA working capability exists and was verified.nothing: closed
resolvedSatisfied without building anything.nothing: closed
absorbedFolded into another document that now carries it.nothing: closed
discardedRejected.reviewing, through one revisited event

A move to delivered, resolved or absorbed must say where that happened, with closes_with pointing at a document, a phase or a commit.

The only reader

fold()

src/db/ideas.py replays the log into current state and checks it as it goes: one created per idea, each status move starting from the status actually reached, and every move in the schema's transition table. Every tool that needs idea state calls it.

The only writer

tools/append_idea.py

Subcommands add, status, annotate, link, amend, revisit, classify and others. It assigns the next id, stamps the real time, validates every event against the schema and replays the log before appending.

Generated view

docs/00-working/ideas.md

A readable list produced from the log by tools/generate_ideas_md.py. It is never edited by hand, and the governance check fails when it is stale.

Ideas are recorded as given and not filtered on the way in (ADR-010). Triage adds findings, the owner decides, and a promoted idea's plan or requirement is drafted under docs/00-working/promoted/ until it becomes a governed document (GOV-011).

A typical path through all four: the owner names a want, and it is appended as an idea. Triage links it to related work. The owner promotes it, and it gets a PLAN code from the allocator. The plan's phases go into the backlog, naming the idea in their ideas field. An agent claims a phase, works it in a worktree and records the session in a SESS document. When the work ships, the idea closes as delivered, pointing at the commit or document that delivered it.
