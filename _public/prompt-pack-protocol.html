D‑SystemPrompt-pack planning protocol
    Governed build methodology · GOV‑008

    One session manufactures the pack. A second session spends it.

    A prompt pack is the complete governed artifact set a multi‑agent build runs from — requirement, decisions, plan, backlog phases, roster deltas, delegation prompts, coordinator prompt and kick‑off record. This page is the protocol for manufacturing one: eight stages, four adversarial gates, nothing authored mid‑build.

    Authority. The authoritative text is the prompt-pack planning protocol (GOV‑008, docs/08-governance/); its adoption as the standard for multi‑agent builds is recorded in ADR‑017. This page is a rendering of that protocol, not a second copy of the rules — where they differ, the governed documents win.
    01

    The core split#

    Planning and building are different kinds of work, done in different sessions, with a hard boundary between them.

    ▾
    The planning session manufactures the pack. The build session spends it — via verbatim dispatch. If the planning session did not write it, the build session does not send it.

    Session onePlanning

    Interactive, owner‑in‑the‑loop. Ratifies decisions through question batches, investigates the repository, and writes every artifact the build will need — through the eight‑stage pipeline below.

    The boundaryVerbatim dispatch

    Every build prompt is pre‑crafted and idempotent. A missing prompt is a blocking finding for the owner, never something to improvise. This is what makes the build resumable, auditable and cheap.

    Session twoBuild

    A coordinator claims nothing, writes no code, and dispatches pre‑built orchestrators with their pre‑crafted prompts. Every re‑run of the same coordinator prompt is a resume, not a restart.

    Why the boundary holds

    Authoring during a build mixes two failure modes: judgment made under schedule pressure, and prompts nobody reviewed. The pipeline moves all authoring into the planning session, where each artifact passes an adversarial gate before anything downstream depends on it. The build session then has exactly one job — execution against frozen inputs — and its failures are legible: either an input was wrong (a planning defect, caught by audit next time) or the execution drifted (a coordinator defect, visible in the report).

    02

    Anatomy of a prompt pack#

    Every artifact the pipeline produces. All are governed documents with allocated codes — except exactly one.

    ▾
    The one untracked artifact. The kick‑off paragraph is delivered in chat so the owner can paste it into the next terminal without hunting for files. Its durable copy is the kick‑off record’s final section — the chat delivery is a convenience copy, and everything else on this page is governed.
    03

    The eight‑stage pipeline#

    Stages produce artifacts; gates freeze them. Owner sign‑off at a gate means later changes go through the same gate again. Hover or click any node.

    ▾
    Mahogany edges and nodes are the owner’s territory: gates, ratification, and the paste that starts the build.

    Gates freeze, they do not decorate

    A gate that passes means the artifact is frozen; a change afterwards re‑enters the same gate. The workbench pack audit caught five real defects before execution — including a dispatch plan the claim validator would have rejected mid‑build.

    A and B are never one document

    Prompt A is the owner’s input; Prompt B is the machine that turns it into artifacts. Keeping them separate makes the review gate between them real: B is audited against A, and sign‑off has a definite object.

    04

    Standing rules#

    Five rule groups that travel with every pack, whatever it builds.

    ▾

    ContextSelective injection

    Context loads when the step that needs it begins, never up front. Short parents defer to children; the delegation pack is dispatched verbatim one section at a time. Nothing front‑loads the full pack into any agent’s opening context.

    DisciplineAgent hygiene

    The coordinator claims nothing and never does a worker’s job. Claim budgets and path locks are checked numerically before claiming. Validators receive the diff, the requirement and the commands — never a creator’s rationale. Truncated agents are resumed, not re‑run; assertions are verified against real output.

    SpendCost protocols

    Haiku for mechanical gates. Sonnet is the standard model for judgment work. Opus is never pre‑assigned — at most one documented escalation per build, only when absolutely necessary. Two fix cycles per item; what survives them is reported, not looped on.

    CadenceGate check‑in policy

    Prompt A always asks the owner up front: stop at gates for check‑in, or push through to close‑out? The answer lands in the kick‑off record, never assumed. A critical issue first gets a dual review — an adversarial agent attempts a solution — and pauses for the owner only if it survives unresolved.

    And always
    • Descope is the owner’s alone. The pack drafts the ladder for emergencies, but no rung is taken without explicit direction unless the kick‑off record grants a stated exception.
    • A failing check is a result to record, never a step to retry until quiet.
    • Every document code comes from the allocator (--next-code), and the artifact set is called a prompt pack — never a “workbench”, which names the UI product.

    Case study — the live demo build#

    The first run of the shape, before it had a name: six phases, ten agents, a rehearsed demo.

    ▾

    The packFactory output

    The agent factory (PROMPT‑010) manufactured the roster, the governance documents and the delegation pack (PROMPT‑018) in one planning session — deferring its detailed specifications to child documents read only when their step began.

    The buildCoordinated spend

    The build coordinator (PROMPT‑014) dispatched the pack verbatim across the six demo phases — terminal backend, stage frontend, overview tools, overview skill, content and rehearsal, stage interaction — under the two‑fix‑cycle cap and the completion gate.

    What it proved
    • Verbatim dispatch scales. Ten agents worked from pre‑crafted prompts with no mid‑build authoring, and the track closed audited‑complete.
    • Selective injection holds context budgets down. Parent prompts stayed around a hundred lines while the pack carried the detail.
    • The shape was reusable. PROMPT‑010 said so at the time — “single‑use in intent, reusable in shape” — and the workbench run proved it.

    06

    Case study — the workbench build#

    The second run added the full gate structure — and its audits caught real defects before a single line of build code.

    ▾

    The packPlanned against a deadline

    The pre‑plan package (PROMPT‑020) carried the owner’s ratified decisions and open questions into a planning session that produced the requirement (REQ‑007), three decisions (ADR‑014..016), the plan (PLAN‑022), seven phases and the delegation pack (PROMPT‑021) — one week before the demo that presents the result.

    The gate that paidFive findings

    The adversarial pack audit (commit 804c6c7) found a parallel dispatch the claim validator would have rejected numerically, a notes picker fed from the wrong source, a supersession that was asserted but not recorded, and clipboard assertions no validator could check. All fixed before execution.

    What it added to the protocol
    • The kick‑off record (PROMPT‑023): per‑build owner rulings — pre‑approved integration, owner‑only descope, a bounded enhancement lane — in a governed document that wins over the coordinator prompt where they differ.
    • The dual‑review rule for critical issues: an adversarial agent attempts a solution before the build is allowed to pause for the owner.
    • Numeric claim‑budget checks: the conflicts column says nothing about the budget, so the budget is counted, not eyeballed.
